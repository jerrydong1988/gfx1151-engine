## 两种 v2 实现的差异

| 部分 | 本分支路径 | 上游路径及本轮融合 |
|---|---|---|
| 稠密 HT 投影 | 预解码 BF16，或本分支 native HT | 上游融合旋转/解码/GEMV，减少带宽与启动开销 |
| 专家 Prefill | exact、补偿与 grouped 等模式 | 上游 FP16 中间张量与 LUT WMMA、融合归约/旋转/共享专家 |
| MTP 短验证 | aligned 策略及本分支小批次累加 | 融合方案在不超过 16 行时保留本分支专家路径 |
| split-K 归约 | 本分支原路径保持 | 上游原实现使用浮点 atomicAdd；新增固定 split 顺序归约 |

**FP16 与 BF16 不是简单的“一个精度高、一个精度低”。** FP16 尾数位更多而范围更窄，
具体误差还取决于旋转、激活拆分和累加顺序。native HT 避免了一次完整权重 BF16
物化，也会与这个 BF16 参考产生差异。不能只比较吞吐或首选 token 比例就宣称模型质量更好。

精度保守的 `exact` 默认路径仍保留。下面的性能候选沿用 R18 的
`grouped + native HT` 研究设置，**不是 exact 模式的测速**。

## 固定顺序 HT 的诊断

原上游 HT 使用多个 block 对同一 float 地址做 atomicAdd，抵达顺序影响最后几位。
相同输入重复运行的微核实验直接复现了这一点。本轮可选 `GDEC_V2_HT_ORDERED=1`
为每个 split 保存独立结果，最后到达的 block 按固定顺序归约；保留一次 kernel launch，
没有把输出强制舍入成某个参考值。

测试由独立 CPU HGN 解码的 FP32 权重及 FP64 dot 得到参考。覆盖 FP32/BF16 输入、
1–8 行、128×128/256×384/1024×2560/256×10240 投影、单 split 和多 split，
每组重复 8 次，并比较多行第一行和单行输出。已测试的 ordered 路径全部逐位重复、
跨行首行一致，相对 L2 误差约 10^-7。测试：`tools/hgn_v2_upstream_test.cpp`。
这证明了这些内核样例的数值性质，不是任意上下文下整模型质量的证明。

## 数值比较的含义

2040 个 teacher-forced 位置来自 8 段 512 token 的合成混合语料。参考为**同一份
量化权重在原分支 exact 模式的 logits**，不是未量化 BF16 模型真值。

| 计算路径 | Mean KLD | 与参考首选 token 一致率 |
|---|---:|---:|
| 整合后 exact | 0.000000（显示精度） | 100.000% |
| 原分支 grouped/native HT | 0.021769 | 96.765% |
| 整合后保留原分支计算 | 0.021769 | 96.765% |
| 原上游 v2 | 0.027064 | 96.275% |
| 整合后两部分均用原上游计算 | 0.027064 | 96.275% |
| 仅使用原上游稠密计算 | 0.018939 | 96.373% |
| 仅使用原上游专家计算（全部行数） | 0.017817 | 96.765% |
| 最终 ordered 稠密 + 上游大批次专家 | 0.027064 | 96.275% |
| 最终仅 ordered 稠密计算 | 0.018939 | 96.373% |

“专家全部行数”是数值拆分实验，**不是**性能表里的“仅大批次专家”候选。
对应的 prefill/verify 行数选择不同。较低 KLD 只表示更接近此参考分布；不能据此
声称统计、代码或事实准确率一定更高。本轮后续的真实工具任务采用独立结果判分。

整合后 exact 的 99.9 分位 KLD 为 0.000049；参考文件保存 logits 时存在量化/压缩。
因此 mean 显示 0、首选 token 全部一致，也不能写成所有 logits 逐位相等。

## 连接、缓存和容量验证

- 56 项 API 工具参数/失败路径测试、单/双槽位断连测试通过。引擎连接模拟为不响应取消
  时，API 在约 11 秒后释放该连接并让后续请求继续；修复前的对照仍在等待。
- 最终引擎在两种计算路径、单/双槽位上共通过 48 项真实协议检查，覆盖拒绝后排空
  VIMG、错误帧、上下文拒绝、三类短任务、两个采样种子的各模式重复、并发与取消重用。
  随机采样检查的是模式内部重复及合法输出，不是串行/MTP 的随机分布等价证明。
- 私有 SSD KV 缓存：原路径首次命中 0，重启后命中 768 且输出一致；切换融合路径后
  命中 0。证明本次策略指纹隔离生效，没有跨算术策略恢复缓存。
- 两槽位共享 16384 token 页池：14000 输入请求仍在生成时，4096 输入的新请求被
  容量保护明确拒绝且没有输出；先前请求完成后，同一连接重试成功输出 16 token。
- 独立 benchmark 在原分支计算和融合计算下均完成；格式/边界、overlay、映射去重、
  PLE 预取与共享 KV 的 host 测试通过。四个启动入口的 32 项配置检查通过。

保留了中间失败的证据：首个 Agent 运行在调用模型前被 fixture 目录保护拒绝，修正
测试输出目录后重跑；原生启动器首次重定向配置检查失败，修正 `CONOUT$` 后重跑通过。
这些不能算作模型推理失败，也未将其混入模型任务成功率。

## 开关与复现

| 变量 | 值与作用 |
|---|---|
| `GDEC_V2_DENSE_BACKEND` | `fork`（默认）或 `upstream` |

`SPEC_PRECISION`、`SPEC_SERIAL_ORDER_MR`、`V2_MOE`、`V2_NATIVE_HT`。
没有配置时保持原来的默认行为。`exact` 只约束本分支专家路径；显式选择 upstream
不会神奇地使上游 FP16 专家变成 exact。

### Windows 可切换配置

`tools/start_windows_profile.ps1` 支持系统自带 Windows PowerShell 5.1 及 PowerShell 7。
它只设置新启动器的进程环境，不改写 `service.conf`、注册表、用户环境变量或权重文件。
启动前须退出已有实例；原生启动器仍负责互斥、端口检查、托盘与子进程生命周期。

```powershell
.\tools\start_windows_profile.ps1 -Profile v2-exact -ModelDirectory C:\path\to\weights -Check
.\tools\start_windows_profile.ps1 -Profile v2-hybrid -ModelDirectory C:\path\to\weights
```

配置值在 `tools/windows_profiles.json`：`v2-exact` 保留本分支保守计算，`v2-fork`
使用 grouped/native HT，`v2-hybrid` 使用本轮融合，`w4b` 使用旧主文件、overlay 和
外部 MTP。这些预设固定为 262144 上下文、8192 分块、单槽位、BF16 KV、aligned MTP；
v2 的 gamma 为 2，w4b 为 4，RAM/SSD 检查点关闭，视觉塔启用。现场测试记录会另外
区分纯文本测速与带视觉塔的兼容性测试。`IPROJ_SOLUTION=-711` 是本机运行库验证过的
研究设置，不保证其他 GPU/运行库存在同一 solution。

本轮 Agent 三组比较都使用同一整合后 API、相同客户端及最多两次工具拒绝恢复。
因此它比较计算路径在固定工具环境里的表现，不是原上游完整 API 栈与本分支的可靠性排名。

## 如何选择

- 严格保持本分支原有参考行为：选择 `v2-exact`。它在本轮 2040 个位置全部保持首选
  token，仍不代表所有输入、随机采样或上下文长度都已证明等价。
- 追求本机 v2 吞吐及较少 arena 预留：选择 `v2-hybrid`。它结合上游大批次专家、
  ordered HT 和本分支短验证/MTP 修复；应以具体任务校验质量，不把它称为无损 exact。
- 需要追踪此前 grouped/native HT 行为：保留 `v2-fork` 作为对照。
- 继续使用原来的旧权重：保留 `w4b`，不把 v2 专属专家加速套用到旧格式。

因此本轮的结论是**融合有明确的受控吞吐/内存收益，保精度模式和旧路径仍有保留价值**，
而不是其中一套实现全面胜出。长输入短输出可以选串行；已经验证的这两类持续输出
Agent 任务可从 MTP 获益。后续需要更多业务数据与重复任务才能判断普遍任务质量和耗时。
