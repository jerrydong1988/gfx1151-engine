# R18：任务可靠性、工具参数校验与有界恢复

日期：2026-10-02。设备仍为 Windows 11 / Ryzen AI Max+ 395 / Radeon 8060S /
128 GiB UMA。基线源码为 `23fd2e26a0982e7469b5ebddbb15c288e776f8e5`。
本轮关注完整任务能否正确交付，未改变模型权重、KV 精度或 GPU 计算内核。

## 根因：模型、工具环境和协议都有问题

R17 办公任务确实生成过错误 SQL：将 `row_id` 纳入业务去重、提前排除冲突记录，
以及引用不存在的 CTE。未知工具名 `query_ledser` 也是实际模型输出。
这些不能全部归因于 API，也不能靠更快的 Decode 修复。

同时，复查发现合成账库工具的只读 authorizer 误拒绝了合法查询：SQLite 对 CTE
`count(*)` 可能发出没有数据库名、列名为空的 `SQLITE_READ` 回调。旧实现只允许
真实表名 `invoices/payments`，导致此类查询返回 `not authorized`。R18 允许这类
派生关系读取，仍限制底层真实表。首次候选过于宽松，测试发现其允许统计
`sqlite_master`，随后补充了真实关系/元数据排除；正式测试使用修正后的版本。
只读连接、query_only、单语句、返回行数限制、SQL 时间预算都保留。

这说明旧失败样本混合了模型错误和测试工具错误。R17 原始日志和失败结果保留，
不重新包装成纯模型能力结论。这个 SQLite 修复属于本地测试工具，不是 Octop 的
数据库实现或 GPU 内核修复。

## 本轮改动

1. API 在工具调用闭合时校验常见参数结构：类型、必填字段、枚举/const、嵌套
   对象/数组和额外字段。重复 XML 参数明确失败，不再使用最后一个值覆盖。
   支持的组合 schema 进行校验；包含未知约束或未解析引用的组合不据此误判。
2. Chat 和 Responses、流式和非流式都给出有界错误诊断，包括错误工具名或字段
   路径。诊断不回显参数值；工具参数本身仍按原协议流式传输。另修复大浮点数
   转有符号整数的上边界判断，并测试 UTF-8 名称截断。
3. 提供客户端恢复策略：仅在明确 `invalid_tool_call` 后重新生成，整个任务最多
   两次，不重试相同诊断。失败响应的全部半截调用都丢弃；不猜工具别名、不替换
   参数，不重复执行已成功的前序动作。超时、网络错误、length 不自动重试。
4. 把办公提交要求明确写成 tool schema，代码任务也使用对应的结构。仅提供字段
   和类型，没有加入正确金额、SQL 答案或评分反馈。办公独立评分继续拒绝额外字段、
   错误类型与错误数字。
5. 将合成账库、受限函数工具、客户端、独立复算和故障注入测试纳入仓库，便于
   以后修改时复现。带本机路径与进程身份保护的 Windows 启停驱动保留在本地。

这是输出校验和客户端恢复，**不是 constrained decoding 或完整 JSON Schema**。
`$ref`、数值范围、字符串正则等未实现的约束仍需消费者验证。流式消费者必须等
整个响应成功结束再执行工具；提前执行 argument delta 不能获得本轮客户端的保护。

## 思考开关的诊断对照

先使用旧 R17 API、修正 CTE 误拒绝的初步工具版本、原宽松提交 schema，保持
MTP、greedy、每轮 4096 输出 token、最多 24 轮及一次通用错误反馈一致，只改变
`enable_thinking`。这两次先导测试尚未采用正式版本的元数据读取防护。

| 条件 | 结果 | 任务耗时 |
|---|---|---:|
| 关闭思考 | 24 轮仍无结构化提交，max_turns | 265.08 秒 |
| 开启思考 | 13 轮自然结束，要求的统计值全部正确；额外提交 cutoff_date/notes，严格评分失败 | 424.61 秒 |

额外字段是提交契约不一致，不应称为统计数字错误。也不能把 24 轮未完成解释成
无限预算必然失败。这个小对照支持为复杂统计任务保留思考预算，但不是广泛能力
估计，更不是对量化损失的测量。

## 条件、验证和边界

正式任务使用主 HGN v2 + PLE sidecar，单槽位、262144 上下文容量、BF16 KV、
8192 Prefill 分块；持久 prompt cache 关闭，同一会话仍复用前缀。grouped/native HT
及累计研究开关沿用 R17，其中 QSA 两个实验开关在本轮均开启。MTP 为 aligned、
gamma 2，固定 greedy、seed 20261001，思考开启，每轮最大 4096 输出 token、
最多 24 轮，错误重新生成最多两次。没有连接 Octop 历史记忆。

`amounts-v2` 改变发票、付款金额以及由此得到的余额和 Top5 金额；Top5 的 ID/顺序
在本次变体中未改变，ID、业务类别、日期和规则也不变。因此是一次金额扰动检验，
不是完全不同领域或随机任务分布。

任务耗时包含失败请求、恢复、模型各轮及工具执行，不含模型加载和最终独立评分。
Prefill 只用新增 token / 阶段耗时，Decode 用生成 token / 阶段耗时；保留失败请求
的实际 reqstat。不能把累积上下文或缓存命中 token 当成新计算吞吐。

CPU 验证：46 项 fixture 检查、12 项 CTE/拒绝行为检查、两套数据共 12 项独立
SQL 对 Python 复算、29 项原客户端测试和 6 项新增恢复循环测试通过；另有恢复
次数、重复错误、禁用和非协议故障的边界断言。API 通过 14 案例 × Chat/Responses
× JSON/SSE = 56 组协议检查、完整 API 回归和断连取消回归。解析器测试同时覆盖
整段与逐字节输入、嵌套字段、重复参数、UTF-8 和整数边界。

公开的 fixture 额外把数据变体写入每次运行的元数据，以便以后独立复算不会误用
进程当前的变体；两项额外 CPU 检查覆盖此行为。同一变体的数据、规则和提交
schema 未改变。实机实验保留当时冻结脚本的 hash，公开版本的差异另行记录。
