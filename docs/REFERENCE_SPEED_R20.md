# R20：在参考数值行为下追回速度

2026-10-02，Windows 11 / Ryzen AI Max+ 395 / Radeon 8060S / 128 GiB UMA。
研究基于 R19 `22920b7e6fb4c0194fc291ea5eb1b08bccb964c3`，使用同一份
Halogen Flash-Next v2 HGN 和 n-gram 文件。未重新量化、改写权重或调用 Octop。

## 目标与判定

目标是尽量保留 R19 hybrid 的速度收益，同时恢复原 exact 路径的参考行为。
参考是同一量化权重的原 exact 实现，不是未量化模型真值。R19 hybrid 的
96.275% 首选 token 一致率也不是任务正确率。

本轮新增可选的 FP32 专家输入复用内核，保留每个 lane 的乘加次序和最终归约顺序。
该候选仍使用参考稠密投影，不能把它表述为“原 hybrid 已在所有路径无损”。
所有新增计算开关默认关闭，日常部署和旧 w4b 路径没有被本轮替换。

## 差异定位与尝试

使用固定输入、固定量化权重，以 exact 为共同底座逐项替换，原始 8 段 512-token
语料共 2040 个 teacher-forced 评分位置：

| 替换部分 | 相同首选 token | 不同位置数 |
|---|---:|---:|
| 原 exact | 100.000% | 0 |
| R19 hybrid | 96.275% | 76 |
| 只替换上游稠密路径，保留 exact 专家 | 96.863% | 64 |
| 只替换上游专家 Prefill，保留参考稠密 | 96.716% | 67 |
| 只用 grouped 专家，保留参考稠密 | 96.961% | 62 |
| 只用 compensated 专家，保留参考稠密 | 96.765% | 66 |
| grouped 恢复逐专家逆变换和原路由顺序 | 97.255% | 56 |

这些拆分的底座和 R19 部分表格不同，不能直接按标签跨表相减。
层间诊断的首个差异：上游稠密在第 0 层注意力输出；专家候选在第 0 层 MoE 输出。
最小的一组初始最大绝对差仅约 2.98e-8，但后续 BF16 舍入和路由可以放大差异。
因此只对最后 logits 的近似平局做修补，没有解决前面计算图已改变的问题。

另写了保持原 Hadamard 变换顺序与缩放结合顺序的流式 HT 解码器：
12 组种子/形状的 BF16 权重逐位相同，590 个实际投影张量的逐位比较也无差异。
大矩阵解码微测试约快 4 倍；原实现多数在加载时解码，这不是 4 倍推理提速。
该实验还恢复了参考 lm_head 缓存和 indexer 的 CPU FP32 权重解码。
部分早期观察轮有 2–8 个不同 token，后续重复轮达到 2040/2040；原因尚未严格定位，
不能把它当作全路径等价证明。特别是小批次 native HT GEMV 仍改变浮点计算路径。
这条流式稠密实验没有混入下方的保精度候选。

## 保精度专家内核

`GDEC_V2_EXACT_REUSE=1` 仅替换既有 exact 大批次专家分支；短批次、aligned MTP
验证和串行后备路径保留。每个累加器仍按 `c = lane + 32*j` 的原次序执行 FP32 FMA，
随后按 `16, 8, 4, 2, 1` 做 wave 归约。优化点是跨输出行/输入 token 复用数据，
调整 tile、寄存器占用、packed int4 读取和循环展开，不改变权重精度。

六轮微内核搜索共 216 个形状/候选记录，逐位输出、尾部和前后保护区域均通过。
测试包含 67-token 非整齐尾部、513/8192-token、512 专家、gather/identity 两种输入。
大 tile 寄存器溢出、部分 LDS staging 和过度展开会变慢，未据此设置默认。

| 8192-token 微核 | 参考 ms | 最终候选 ms | 加速 |
|---|---:|---:|---:|
| gate/up，D=2560，M=1280 | 228.233 | 92.238 | 2.47x |
| down，D=640，M=2560 | 142.294 | 70.860 | 2.01x |

这是单算子时间，不能直接相加或充当端到端收益。

## 独立整模型数值复验

| 输入集合 | 评分位置 | 首选 token 与参考一致 | 全词表原始 FP32 指纹 |
|---|---:|---:|---|
| 原 8 x 512 | 2040 | 100% | 相同 |
| 新办公/代码/科学，3 x 1024 | 1533 | 100% | 相同 |
| 新 8192 | 4095 | 100% | 相同 |
| 新 16384，跨两个 Prefill 分块 | 8191 | 100% | 相同 |
| 合计 | 15859 | 100% | 13 个上下文均相同 |

前 3 组同时对照不可变的 R19 原二进制参考文件；16K 新参考由未启用新核的基线路径生成。
完整词表指纹在最终同一二进制下比较新核开/关，覆盖每边 3,938,106,880 个 FP32 值，
使用逐个 uint32 的 64-bit FNV-1a 摘要。这比只比 argmax 或压缩 KLD 更严格，
但仍是有限输入的观测，不是对任意输入、硬件和未来编译器的证明。

KLD 参考文件保存的是压缩的 log-probability；长输入的压缩 PPL 与原始 PPL 可不同。
本轮额外保留原始 logits 指纹，避免误把序列化误差归因于计算内核。
最终编译后另有两处主机策略修正（严格开关判断、实验策略的 KV 指纹隔离），
已核对 `.hip_fat` GPU 程序段 SHA-256 与上述数值测试二进制相同。

## 完整请求计时

三组使用相同输入和相同容量：原 R19 exact、
本轮 exact-reuse、R19 hybrid。256/9217/32768 输入，各生成固定 128 token，
greedy、gamma 2、8192 Prefill 分块、单槽、BF16 KV、上下文容量 34816；
每个长度串行/MTP 各两次，第二次反转两种模式顺序。每次验证缓存命中为 0。
完整请求时间不含权重加载、tokenization 或外部工具执行。

以下为两次测量的中位数；PP/TG 单位均为 token/s，完整范围保留在 JSON 中。

| 输入 | 模式 | 原 exact PP / TG | 新候选 PP / TG | hybrid PP / TG | 完整请求秒：原 / 新 / hybrid |
|---|---|---:|---:|---:|---:|
| 256 | 串行 | 220.04 / 15.28 | 358.64 / 15.19 | 549.59 / 35.10 | 9.55 / 9.14 / 4.12 |
| 256 | MTP | 218.18 / 19.01 | 350.97 / 19.64 | 544.31 / 41.32 | 7.94 / 7.25 / 3.57 |
| 9217 | 串行 | 343.49 / 14.93 | 611.78 / 14.94 | 1257.12 / 33.54 | 35.43 / 23.64 / 11.15 |
| 9217 | MTP | 345.02 / 19.16 | 614.35 / 19.25 | 1266.66 / 42.72 | 33.40 / 21.66 / 10.28 |
| 32768 | 串行 | 350.84 / 14.99 | 638.71 / 14.70 | 1421.60 / 32.67 | 101.98 / 60.04 / 26.99 |
| 32768 | MTP | 344.60 / 18.00 | 630.76 / 17.87 | 1406.11 / 36.80 | 102.21 / 59.12 / 26.79 |

32K 下新候选的 Prefill 提高约 82%–83%，完整请求减少约 41%–42%；9K 减少约
33%–35%，256-token 短输入则只减少约 4%–9%。Decode 没有明确收益，不能把
Prefill 的倍数推广到整个生成阶段。32K MTP 比串行约快 0.91 秒，样本仅两次，
不能据此宣称已解决所有长输入负收益。

与 hybrid 相比，新候选 32K Prefill 仍只有约 45%，请求时间约为其 2.2 倍。
若按“相对原 exact 节省的请求秒数”计算，新候选保留约 56%–57% 的 hybrid
时间收益；这是明确口径下的局部量化，不是宣称完整目标已经实现。
保精度候选 arena 预留 85.66 GiB，hybrid 为 77.83 GiB；新候选没有取得这部分
约 7.83 GiB 的内存节省。arena 不是 Windows 总提交量或实测峰值。

12 组新候选/原 exact 的 128-token 自由生成序列全部相同，共 1536 个输出 token。
三组各自的串行/MTP 配对共 18 对也都相同；这不表示 hybrid 与 exact 输出相同。

编译后检查新核指令：已大量使用 dual FMA，均未发现 scratch spilling。
不是遗漏了一个简单双发射编译开关。


## 真实 API 工具闭环

使用独立的六行合成台账，要求先按 id 去重，再排除已结记录，保存记录数、总额和
两部门金额。通过实际 HTTP API 自动调用 `read_ledger` 和 `save_summary`，再完成最终回复。
两种模式均 3 轮通过：4 条有效记录，32050 分总额，研发 20250 分，销售 11800 分，
与测试脚本从原始行独立计算的 oracle 完全一致。没有纠错提示或自动重试。
请求统计核对了实际 drafter 及 usage。串行用时 18.59 秒，MTP 11.97 秒；
两边输出 token 总数均为 242。此小任务验证接口与基本工具闭环，不替代大型合同台账审计，
也不证明模型的统计能力已经改善。

## 开关与复现入口

- `GDEC_V2_EXACT_REUSE=1`：在 `GDEC_V2_MOE=exact` 的大批次分支启用新核。
  上表保精度候选还要求 `GDEC_V2_NATIVE_HT=0`，不启用上游稠密/专家 backend 或其他实验数值开关；
  完整环境记录在下方 JSON。仅在任意 hybrid 配置中增加此开关，不能得到上表结果。
- `GDEC_V2_HT_DEQ_EXACT=1` / `GDEC_V2_REFERENCE_HEAD=1`：流式稠密实验；不是上面的通过候选。
- `GDEC_V2_GROUPED_RANK_ORDERED=1`：grouped 数值拆分实验；仍不等价。
- `GDEC_KLD_RAW_HASHES=<file.csv>`：记录完整词表的原始 logits 指纹。
- `GDEC_KLD_DIAGNOSTICS=<file.csv>`：逐位置 argmax、margin、KLD。
- `GDEC_NUMERICAL_TRACE_DIR=<existing directory>`：采样层间张量，默认第 0 个 Prefill 分块。
  `GDEC_NUMERICAL_TRACE_CHUNK` 可选其他分块；该诊断会同步 GPU，不用于测速。
- `GDEC_LT_CHOICES=1`：记录实际选择的 hipBLASLt 算法，用于解释跨轮变化。

微核工具是 `tools/v2_exact_batch_bench.cpp`、`tools/v2_exact_dense_bench.cpp`，
在配置好的 HIP/Visual Studio 开发环境使用：

```text
hipcc -O3 -std=c++17 --offload-arch=gfx1151 tools/v2_exact_batch_bench.cpp -o build/v2-exact-batch-bench.exe
hipcc -O3 -std=c++17 --offload-arch=gfx1151 tools/v2_exact_dense_bench.cpp -o build/v2-exact-dense-bench.exe
```

数字汇总见 `docs/benchmarks/r20-reference-speed.json`。大模型计时与 GPU 微测试必须串行运行，
不要在被测实例上同时跑其他推理或 profiler。
