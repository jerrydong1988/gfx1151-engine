# 32 张图片扩容验收 — 2026-10-07

本地部署配置由 16 张提高到 32 张；API 与底层 GEN/VIMG 协议共用 `src/vision_limits.h`，
避免两层上限不一致。按一次请求的全部消息累计计数，历史图片同样计入。
API 未配置时仍默认 8 张；`MAX_IMAGES="32"` 由现有原生启动器传入。
必须成对替换 API 和引擎，仅修改配置或只换 API 无法支持 17–32 张。

## 精度、资源与性能取舍

- 未修改权重、量化、视觉缩放、视觉编码、GPU 算子、MTP 或精度优先参数。
- 新旧引擎 PE 的 `.hip_fat` GPU 代码段共 4,948,992 字节，
  SHA-256 均为 `d3617c9cf16e40791c5f3bd7eaf84aef5c58125a05afa3824103d9f174eb3485`，逐字节相同。
- API 图片预处理结果逐值比较一致；同输入文本的生成 token 序列集合一致。
- 不预留 32 张图片的内存。检查只发生在每张图片进入预处理／接收阶段，
  不进入逐 token 或 GPU 计算循环；原有动态缓冲区、图像缓存路径保持不变。
- 总预算 262,144 patches，即 65,536 个视觉 token、每份 FP32 patch 数据最多 1.5 GiB。
  这不是整个进程的内存上限，传输和执行阶段可能同时持有多份数据。
  可容纳 32 张标准 1920×1080 图片；不会改变旧版 16 张图片在现有缩放范围内的接纳行为。
- 超出总预算时明确拒绝，不自动缩图或丢弃图片；保留既有 64 MiB HTTP 请求体和上下文限制。
  失败路径先排空剩余协议帧，保证后续请求不会被残留图片字节破坏。

## 交错对比

同一台机器、相同权重、双槽／256K／精度优先配置，以旧—新—新—旧顺序独立启动。
每轮包含两次 256／8192 token 文本和 1／4／16 张图片测试，共 40 个可比请求；
每种负载每版 4 个样本，下面为中位数。文本固定生成 128 token，图片为 640×384。
所有测量请求均无 token 缓存命中；独立测试目录和端口不污染部署的请求统计。

图片短输出的排版及输出 token 数有少量波动，不能据此宣称 Decode 提速。
首轮预检提示允许模型把三位数拆开返回，已停止该轮；正式四轮统一使用修正后的提示，

- 16、17、20、32 张图片逐张读取独立三位编号，全部内容和顺序正确。

- Responses 路径的 32 图请求通过；双槽同时处理各 17 张图片通过，观察到 2 个在途请求。
- 32 张 1920×1080 图片读取首／中／尾编号通过，总耗时 110.06 秒，
  输入 65,411 token、首字 107.29 秒。
  新增图片本身增加编码和 Prefill 工作量，这与原有请求的性能回退不同。
- 第 33 张图片在 API 层被拒绝，随后普通请求成功。
- 真实底层连接的 33 帧超限、总 patch 预算超限均正确拒绝并排空；同连接 PING 成功，
  之后模型请求正常完成。预算拒绝测试使用分块发送，不在测试客户端创建大副本。
- 99 项预处理／预算／协议／GPU 检查和 90 项 API 回归断言通过。
