# R21：保精度数据流与小收益叠加

2026-10-02；Windows 11 / Ryzen AI Max+ 395 / Radeon 8060S / 128 GiB UMA。
研究分支 `codex/v2-dataflow-r21-20261002`，基于 R20 `524ce41`。
使用相同的 Flash-Next v2 HGN 与 PLE n-gram 文件；没有修改或重新量化权重。

## 新增实现

三个计算开关均默认关闭，日常部署没有被自动替换。

| 开关 | 改动 | 适用范围 |
|---|---|---|
| `GDEC_V2_EXACT_ORDER=1` | 将同一权重行对应的 token 分块相邻调度，增加缓存复用机会 | 需同时启用 R20 `GDEC_V2_EXACT_REUSE=1`；exact 大批次专家分支 |
| `GDEC_V2_EXACT_DATAFLOW=1` | wave 内完成激活变换；将逐专家逆变换和按路由顺序加权合并为单核，减少中间数组读写 | exact 大批次分支；不将逆变换移到求和之后 |
| `GDEC_V2_BF16_GEMV=1` | 调整缓存 BF16 稠密权重的小批量 GEMV 布局与 block 大小 | v2、FP32 输入；串行与明确要求 serial-order 的 MR 路径；其他 MR 累加方式保留 |

保留原权重位模式、每个累加器的 FMA 次序、shuffle 归约树、Hadamard 蝶形次序和
缩放位置。新数据流核不是 R19 的 hybrid 路径，也没有给原 hybrid 建立全场景等价证明。
短 exact 专家计算仍走既有分支；非 exact、旧 w4b、GGUF 不会自动使用新专家核。

## 先定位再改动

R20 exact-reuse 的 8192-token 单个分块，48 层同流 GPU 事件区间合计：

| 专家阶段 | 毫秒 |
|---|---:|
| gate/up | 4616.35 |
| down | 3309.61 |
| 输入旋转 | 37.24 |
| 激活及旋转 | 163.34 |
| 输出逆变换 | 385.32 |
| 加权归约 | 231.54 |

这些是诊断区间，可能包含主机提交间隙；不能把重叠的父子区间重复相加。
剖析与正式计时分开。日志里 `v2_wmma_compute` 是历史阶段名，当前 exact 分支
实际执行 FP32 FMA 核，并没有启用 WMMA。无效事件在日志中计数并剔除。

BF16 GEMV 搜索使用轮换权重，普通形状合计超过 96 MiB；极小尾部样例用于
正确性检查，不能当作 DRAM 带宽结论。单 token 大矩阵收益有限，小批量部分
投影更适合改变布局。未将所有形状统一替换为微测试中最快的一种布局。

独立 wave 旋转在大输入下几乎不加速，未接入主引擎；只保留有价值的激活变换。
逐专家逆变换与归约融合的局部大输入约快 2.7 倍，但它只占一部分总耗时。
改变专家 grid 顺序的局部收益较小，不能据此推断整模型会按相同比例变快。

## 数值验证

| 检查 | 评分位置 | 结果 |
|---|---:|---|
| 原 8×512 输入 | 2040 | 首选 token 全部一致；原始 logits 指纹一致 |
| 独立 3×1024 混合输入 | 1533 | 同上 |
| 独立 8192 输入 | 4095 | 同上 |
| 独立 16384 输入，跨两个 Prefill 分块 | 8191 | 同上 |
| 逐 token 串行 teacher forcing | 255 | 新旧串行路径的原始 logits 指纹一致 |

前四组共 **15,859** 个位置，参考为上一轮不可变记录；串行另用保存的 R20
二进制生成参考。指纹覆盖全词表原始 FP32 logits，而非只比较 argmax 或压缩 KLD。
有限输入上的指纹一致不构成所有输入、所有采样和并发配置的数学证明。

串行参考与候选各自相对批量 KLD 文件的首选 token 一致率均为 97.647%；两条串行
路径彼此相同。这是既有逐 token 与批量路径的差异，不能写成新核的退化，也不能
把本轮描述为输入分块方式全部等价。压缩 KLD 的尾部概率还会产生 PPL 序列化误差。

微测试包含 BF16 GEMV 的 816 个形状/P/布局案例、两轮 wave 变换共 180 例、两轮
融合归约共 60 例，以及 42 个专家 grid 案例，检查有限输出位模式、越界保护区和
非有限值。第二轮激活采用实际 mid=640，第二轮归约使用打乱的 pair 索引。

三轮正式交替对照的中位数；每次固定输出 128 token。

| 输入 | 模式 | Prefill 参考→候选，token/s | Decode 参考→候选，token/s | 完整请求参考→候选，秒 | 耗时缩短 |
|---:|---|---:|---:|---:|---:|
| 256 | 串行 | 359.05 → 370.80 | 15.21 → 15.52 | 9.130 → 8.941 | 2.07% |
| 256 | MTP | 348.73 → 364.05 | 19.33 → 20.97 | 7.360 → 6.809 | 7.48% |
| 9,217 | 串行 | 605.94 → 647.55 | 14.92 → 15.18 | 23.702 → 22.894 | 3.41% |
| 9,217 | MTP | 608.40 → 646.36 | 18.74 → 20.22 | 21.999 → 20.656 | 6.11% |
| 32,768 | 串行 | 641.57 → 679.71 | 14.69 → 15.03 | 59.649 → 57.121 | 4.24% |
| 32,768 | MTP | 646.14 → 679.48 | 17.58 → 18.87 | 58.011 → 55.018 | 5.16% |

18/18 组正式配对请求的墙钟都缩短；18/18 组新旧输出 token 完全相同，共 2304 个候选输出 token。
两个引擎各自的串行/MTP 对照共 18 组，生成 token 也全部相同。

32K 三次墙钟范围：
- 串行：参考 59.606–59.901 秒；候选 56.573–57.273 秒。
- MTP：参考 57.901–59.114 秒；候选 54.909–56.245 秒。

三次重复且范围不重叠，支持这些具体负载下可重复的整体收益；不是跨温度、驱动、并发、
所有输入长度或长期运行的普遍保证。

单开关拆分为每项一次、同一 9217-token 输入；只作方向性证据，不对单项百分比作稳定性承诺：

| 开关 | 串行 Prefill / Decode | MTP Prefill / Decode | 串行 / MTP 完整秒数 |
|---|---:|---:|---:|
| dataflow | 631.50 / 14.77 | 637.78 / 18.97 | 23.265 / 21.203 |
| order | 627.24 / 14.70 | 633.76 / 18.96 | 23.408 / 21.300 |
| gemv | 617.55 / 14.74 | 620.88 / 20.42 | 23.615 / 21.118 |

所有拆分输出均与参考 token 一致。稠密 GEMV 的主要收益在 MTP Decode；
数据流和调度主要改善 Prefill。不同层次的百分比不能简单相加。

组合候选的独立阶段剖析：8K 的逆变换/归约从 385.32+231.54=616.86 ms 降到 222.48 ms；
激活从 163.34 降到 150.45 ms。gate/up 与 down 仍占主要时间，未因外围融合消失。

固定 greedy、BF16 KV、单槽位、gamma=2、8192 Prefill chunk、34816 容量；
256/9217/32768 输入与 128 输出，串行及 MTP。每次模型加载后预热，禁止 prompt
缓存复用；墙钟不含模型加载。原 R20 exact-reuse 与新候选在同设备交替运行。
探索轮 0 中有独立 HIP 编译负载重叠，因此完整保留但从主表剔除；主表只采用
停止编译后的轮 1/2/3。不可用微核加速倍数替代完整请求结果。

## 未采用的协同读取方案

额外写了共享内存暂存 FP32 专家权重、可选暂存输入的二维 wave 分工内核。
60 个形状/布局案例全部逐位与保护区检查通过，但没有性能收益：8192-token gate/up
最好的候选约 165.19 ms，对照 92.21 ms；down 最好约 113.30 ms，对照 74.46 ms。
部分组合达到 256 VGPR 并产生 32 字节 local spill；共享存储/同步也有成本，未对
唯一瓶颈作未经剖析的归因。该路线没有接入引擎或计入候选成绩。
代码保存在 `tools/research/r21_cooperative_exact.inc` 与对应 benchmark，方便后续复查。
仓库内副本重新编译并运行全部 60 个案例，逐位及保护区校验再次通过。

## API 工具任务

使用独立的 6 行合成台账，要求按 ID 去重、保留 open、核算总额和部门额，调用工具保存。
本地 OpenAI 风格 API 的串行与 MTP 都完成 3 轮、242 个输出 token，独立 oracle 校验通过：
4 笔、32050 分，研发 20250、销售 11800。用时分别为 18.218 秒与 11.141 秒。
没有纠错提示、重试、Octop 历史记忆或原业务台账参与；这不是复杂长时办公任务成功率证明。

## 结论与边界

本轮实现小收益叠加：本次配置下，Prefill 约增加 3.3%–6.9%，MTP Decode 约增加
7.3%–8.5%；完整请求约缩短 2.1%–7.5%。串行 Decode 变化较小。
仍未追平 R19 快速 hybrid。R20 历史测试中的 hybrid 32K MTP Prefill 为 1406.11 token/s、
完整请求 26.79 秒；本轮未重跑 hybrid，不能把跨轮数据当成同轮受控对照。
本轮候选 679.48 token/s、55.02 秒，仍有明显差距。

原始量化权重的 exact 实现是比较基准，不是未量化模型真值，也不是答案正确率。
未重跑 60K/260K、多人并发、随机采样全矩阵、长时间 Octop 或大型原始台账。
默认开关保持关闭；本地研究结果未自动推送到 Fork、替换部署或更改任何模型配置。
