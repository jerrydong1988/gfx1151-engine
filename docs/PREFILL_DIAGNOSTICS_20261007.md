### 路径和系统检查

- 当前 Windows 行读取路径每行提交一个 160 B 的 ReadFile；8192-token 批次产生 131,072 个行读取。
  使用 IOCP、OVERLAPPED 和 RANDOM_ACCESS，仍使用 Windows 文件缓存。
- `GDEC_PLE_LOOKAHEAD=1` 不是“所有请求都启用”。当前 `PARALLEL=2` 会触发单槽 lookahead 的
  `reason=concurrency` 限制；这不证明当时存在另一个竞争请求。日志证实普通双缓冲分块预取仍启用。
- 约 47.68 GiB 的 n-gram 表位于 C: 的 HP SSD FX700 4TB，NTFS 文件属性未设置压缩或加密。
  系统可见物理内存约 31.65 GiB，不能假定整张表会常驻文件缓存；此信息不能重建事发时的缓存命中率。
- 本次检查时磁盘健康状态正常，C: 剩余空间约 1.79 TiB；20:24–20:32 的 System 日志
  未找到严重／错误／警告事件。这不足以排除临时延迟、驱动或其他进程竞争。
- 推理引擎 SHA-256 为 `b64f434f569be3a9ac5a44b270616b8f44ef815880984d3ae070da0d9a0beb08`，
  service.conf SHA-256 为 `57ebba151491955304345b4481482b547f1889e7561f71e297c47bba7d0b1a28`，与部署前一致。

## 结论与取舍

已证实的直接瓶颈是 PLE 表读取路径的多秒停顿，包含读取提交与完成等待。
缓存未命中／回收和大量随机小读取是优先验证的解释；磁盘竞争、文件系统过滤驱动、
内存压力等尚未区分。没有事发同期的 ETW／磁盘队列／缺页样本，不能归因到其中某一种。

微软说明 OVERLAPPED 文件 I/O 在特定条件下仍可能同步阻塞，文件缓存是否命中会改变其行为；
这支持调查方向，不证明本次具体系统根因：
[Asynchronous disk I/O appears synchronous](https://learn.microsoft.com/en-us/previous-versions/troubleshoot/windows/win32/asynchronous-disk-io-synchronous)。

保留当前精度、双槽位和页读取默认关闭状态。历史 R24 已验证实验页读取的字节一致性，
但没有证明稳定收益；这次也没有足够证据将其直接切为生产默认。
不通过清空系统缓存、改磁盘策略、关闭安全软件或降低精度来强行制造一个更好看的数值。

## 可复用诊断

离线汇总原始引擎日志（5 秒是调查阈值，不是磁盘故障判定）：

```powershell
python tools/request_timing_report.py <engine.log> --stall-ms 5000 --out timings.json
```

新增 `ple_reads`、`ple_waits`、`lookahead_fallbacks` 和慢批次汇总，保留行号。
对损坏数据明确报错；保留旧日志兼容性，不虚构请求归属或累计 GPU 时间。

需要复现时，在现有模型任务执行期间运行有时限的只读采样：

```powershell
./tools/capture_prefill_io.ps1 -OutPath logs/prefill-io-new.jsonl -DurationSeconds 120 -IntervalSeconds 2
```

记录 UTC 时间、每块磁盘的读延迟／吞吐／队列、可用内存／页面读入、进程 I/O 排名。
不发送推理请求、不重启服务、不读取提示词或命令行、不修改设置、不覆盖已有证据。
进程 I/O 包含网络／设备访问，不能直接当作物理磁盘吞吐；首次速率为 null。
空闲期采样仅验证工具，不能证明发生过的停顿原因。

下一步归因标准：复现时把 PLE 停顿区间与磁盘读延迟、队列、页面读入和进程 I/O 对齐。
必要时再做独立实例的相同输入、多次交错读取策略对照，并验证完整字节与输出一致性。
本轮未重放用户长任务，也未进行冷缓存清空或 I/O 策略 A/B，不声称消除了停顿。

本轮证据保存在忽略目录 `logs/prefill-diagnostics-20261007/`，不包含用户提示词。
