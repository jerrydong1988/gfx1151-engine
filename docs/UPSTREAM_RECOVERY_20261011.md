# API 恢复与 GDN 独立评估 — 2026-10-11

## 结论与整合范围

纳入 API 启动后恢复容量、Windows 主机端构建及诊断客户端修复；不融合本轮 GDN shuffle 候选。
保留正式 v2 权重、原 GPU 引擎二进制、原生启动器、TheRock 10.0 运行库和精度配置。
基线 `170fe1e19f48b11fbb931ac30378e36317b6bf00`，上游审核截止 `153d15c5ab00a0c93dec4f5d6f997b6f32edec8b`。

| 上游来源 | 本地处理 |
|---|---|
| `dd8a945` API 先于引擎启动时恢复槽数 | 移植目标行为，先建立可用的单槽池，再在独立连接上重试 INFO；避免空池、请求连接竞争与容量读写竞争。 |
| `453e83a` 连接等待约束 | 仅吸收有界连接思路；不做全项目改名。保留 socket 真实错误码，明确报告连接超时。 |
| `964cbdb` 主机端构建免 HIP 暂存 | `api`、`launcher`、新增的 `eng-cli` 目标不要求 HIP 编译器，不复制 GPU 库/数据库；仍使用 TheRock clang 和 VS 开发环境。 |
| `153d15c` Windows 诊断初始化 | 只取 `eng-cli` 的 Winsock 初始化；不引入 VerifyPool 调度器。 |
| `e533503` GDN verify shuffle | 独立构建并完成 ABBA 后不纳入：当前配置没有稳定的端到端收益。 |

INFO 成功前，API 用配置上下文和单槽处理请求；引擎不可达时安全返回 502。
重试使用独立连接（连接预算 0.3 秒，INFO 等待 1 秒），前 150 次间隔 2 秒，随后间隔 15 秒。
有效 INFO 到达后，在锁内扩容并唤醒队列；失败、超范围和溢出 INFO 不会停止重试。
`engine_info_ready` 只表示初始协商完成，不是持续存活探针。成功后不再周期探测；运行中改变引擎容量需重启 API。
连接预算不包含 DNS 解析，本部署使用数字回环地址。
Windows 使用 `select` 的写就绪/异常集合并读取 `SO_ERROR`，依据
[Microsoft Winsock 文档](https://learn.microsoft.com/en-us/windows/win32/api/winsock2/nf-winsock2-select)。
本机对未监听端口约 2 秒后才报告拒绝，故 0.3/1 秒预算内返回超时是正确结果；
回归分别检查短预算退出和足够长预算下的实际拒绝码，不把合法超时误判成诊断缺陷。

## GDN 对照与取舍

配置：双路，每路上下文 262144，共享 KV 524288，BF16 KV，Prefill chunk 8192，
aligned MTP、gamma=2，原有全部精度开关和 v2/PLE/视觉权重不变。
只有测试期间把 RAM checkpoint 数设为 0，以确保输入均为冷 Prefill；部署配置仍为 2。
完成 A—B—B—A 四次独立启动。同一 API 用于两臂，隔离 GPU 候选的影响。
最终 API 另加了失败连接错误码保留修复，重建后重新跑完整 API 回归；该修复不改变推理计算。

共 40 个性能请求：256、8192、32768 输入，各生成 256 token；每次启动含两次单路重复和两组双路请求。
下表是各组样本中位数，速度单位 tok/s，斜线前后分别为原版/候选。
Decode 用首 token 后的 255 token 除以引擎 decode 耗时。
双路 decode 计时包含等待另一请求 Prefill 让出设备的时间，不能直接与单路速度作效率比较。
8192 输入按并发搭档分别统计。单路每臂每档 4 个样本，双路每臂每组 2 个样本。
短输入并发组的原版第二轮较慢，造成候选汇总中位数看似更好；第一轮未重复出现相同优势。

| 场景 | 输入 token | Prefill 原版 / 候选 | Decode 原版 / 候选 | Decode 变化 |
|---|---:|---:|---:|---:|
| 单路 | 256 | 570.5 / 576.8 | 43.54 / 43.30 | -0.54% |
| 单路 | 8,192 | 1384.0 / 1375.1 | 40.90 / 40.49 | -1.00% |
| 单路 | 32,768 | 1484.7 / 1482.3 | 38.31 / 38.38 | +0.17% |
| 双路 256/8192 | 256 | 575.7 / 575.0 | 17.05 / 17.43 | +2.23% |
| 双路 256/8192 | 8,192 | 1205.9 / 1204.8 | 27.50 / 28.45 | +3.46% |
| 双路 32768/8192 | 32,768 | 1056.3 / 1054.9 | 25.38 / 25.15 | -0.91% |
| 双路 32768/8192 | 8,192 | 1374.8 / 1375.4 | 9.77 / 9.74 | -0.35% |

GDN 单核在当前 gamma=2 对应的 P=3 时，中位耗时从 14.87 微秒变为 18.28 微秒。
较长 P 的单核收益不能当成当前短步验证的收益，因此没有通过“无精度损失且确有收益”的双重门槛。
原版第一次 32768 输入的 decode 存在较慢样本，完整记录保留，没有删去或只比较该点来宣称候选加速。

数值检查：3 个随机种子 × P=1..65 × 独立/原位输出，共 390 组，输出与递归状态逐位一致。
四种文本夹具各测 greedy 与固定种子采样，四次启动共 32 个输出一致性请求。
相对第一轮原版的 54 组完整请求比较（含性能请求），token、返回的 logprob 与结束原因全部一致。
此外，四次取消后继续请求、八次单图/16 图检查均通过。内存分配记录见结构化结果。
这些结果只覆盖已测输入，不能替代通用模型质量评测；本次未重新做双路满 262144 输入压力测试。

两个早期启动因 Gufo 占用约 80 GiB 显存，原版即分配失败，未进行推理，已排除在统计之外。
用户批准停止 Gufo 后，ABBA 使用原始 arena 留量完成，无须降低上下文、KV 精度或修改持久配置。

## 修复验证与复现

- API 恢复六组：未启动引擎、INFO 停顿、错误/溢出 INFO、带在途及排队请求扩至双槽、Windows CLI 真实连接、旧 INFO 格式。
- 原生连接三组：成功连接、短预算有界退出、长预算收到拒绝时保留实际错误码。
- 90 项 API 协议检查、458 项工具失败检查、49 项断连检查、3 组容量上报及取消 ACK 超时恢复均通过。
- 在仅保留 LLVM、没有 HIP 编译器和 GPU 库/数据库的隔离工具链布局中，三个主机端目标构建成功。
